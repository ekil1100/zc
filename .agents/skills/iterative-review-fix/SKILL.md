# 迭代检视修复

当任务适合用有界质量循环处理时，使用这个流程：先检视当前修改，修复发现的问题，再重新检视，直到没有剩余意见或达到最大轮数。

如果用户只要求 review、只检视、提出“不要修改代码”或类似限制，只输出检视意见，不要进入修复步骤。只有当用户要求修复、迭代修改、处理 review findings，或明确要求检视后继续修复时，才执行完整循环。

## 核心循环

除非用户给出其他限制，否则默认最多执行 5 轮。

每一轮都按以下步骤执行：

1. 编辑前先检视当前状态。
   - 阅读相关文件和已有 diff。
   - 优先关注正确性、需求匹配、回归风险、安全性、缺失边界情况和可维护性。
   - 只有当格式或措辞影响清晰度、行为或用户明确需求时，才把它们作为检视意见。
2. 记录检视意见。
   - 每条意见都必须具体、可执行，并关联到文件或行为。
   - 不要为了进入下一轮而编造问题。
   - 如果没有意见，立即停止循环。
3. 修复本轮意见。
   - 修改范围应限于本轮报告的问题。
   - 保留无关的用户变更。
   - 优先沿用项目现有模式，而不是引入新抽象。
4. 验证修复。
   - 运行最窄但有用的检查，例如测试、lint、类型检查、渲染检查或结构化校验。
   - 如果检查无法运行，说明原因，并继续进行人工验证。
5. 从更新后的状态开始下一轮。

遇到以下任一情况时停止：

- 某轮检视没有发现问题。
- 已达到最大轮数。
- 遇到需要用户输入才能安全推进的阻塞问题。

## 检视标准

按以下顺序优先处理检视意见：

1. 功能 bug 或错误行为。
2. 遗漏或违背用户需求。
3. 安全、隐私或破坏性操作风险。
4. 集成点损坏、schema 无效或文件格式错误。
5. 高风险修改缺少实际验证。
6. 可能导致后续误用的清晰度和可维护性问题。

避免无意义改动：

- 不要只为了风格重写可工作的内容。
- 没有证据表明需要扩大范围时，不要扩大任务。
- 当剩余内容只是偏好而非问题时，不要继续循环。

## 沟通方式

保持用户知情，但不要倾倒原始检视笔记。

工作过程中：

- 说明当前正在进行第几轮。
- 用简洁语言总结检视意见。
- 编辑前说明将修复什么。

最终回复：

- 报告实际运行了多少轮。
- 列出最终修改的文件。
- 总结重要修复。
- 包含已执行的验证，以及无法运行的检查。
- 如果达到最大轮数但仍有剩余意见，清楚列出这些意见。

## 输出模板

最终汇报时使用这个结构：

```markdown
完成：运行了 N / MAX 轮检视-修复。

修改文件：
- path/to/file

处理结果：
- ...

验证：
- ...

剩余事项：
- 无
```
